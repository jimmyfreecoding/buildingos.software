# 3.13 权限中心

## 需求概述

本系统提供基于 RBAC（Role-Based Access Control）模型的统一权限管理解决方案，支持按角色、菜单、功能按钮、IoT 设备、物理空间和微服务等多维度灵活配置权限。系统以"两轨权限"（Track A 系统访问权限 + Track B IoT 控制权限）为核心架构，覆盖菜单权限控制、功能权限控制、数据权限控制和物理空间权限控制四大管控维度，并通过统一的 IAM 策略引擎实现跨园区、跨组织、跨服务的权限统一解析与执行。

---

## 3.13.1 整体架构

### 模块总览

权限中心包含五个核心管理模块和两个辅助权限模块，通过统一的权限管理入口组织：

**角色管理**——系统角色的 CRUD 管理，支持菜单树勾选分配和功能按钮权限配置，支持系统级角色和空间级角色两种类型。

**IoT 权限**——基于 IAM 统一策略引擎的 IoT 资源权限管理，支持按组织/部门/用户三级主体授予设备、空间、MQTT Topic 的操作权限，支持权限继承和 DENY 覆盖。

**微服务配置**——按空间（园区）维度控制各微服务的启用/停用开关，实现微服务在园区的可见性和可访问性控制。

**成员管理**——外租企业成员的入职/离职生命周期管理，成员加入组织后自动继承组织的 IoT 策略，离职后自动级联失效所有派生权限。

**服务账号**——面向 WallPad 面板、自动化策略引擎、系统集成接口等非自然人主体的 M2M（Machine-to-Machine）认证与授权管理。

**辅助权限模块**——空间角色管理（物理楼层/区域访问授权 + 日期时间调度）和门禁通行角色管理（门禁分组 + 有效期控制）。

### 技术架构

权限中心采用"前端 Vue 3 + NestJS 后端 + IAM 统一策略引擎"三层架构。前端以标签页形式集成五个管理子模块（角色管理 / IoT 权限 / 微服务配置 / 成员管理 / 服务账号），通过 `/@/api/iam.ts` 和 `/@/api/roleManagement.ts` 两个 API 层与后端通信。后端提供四个微服务：角色管理服务（`system_role` 表）、空间角色服务（`space_role` 表）、IAM 策略服务（`iam_policy`、`iam_micro_space` 表）和菜单管理服务（`system_menu` 表）。前端 ACL Store 通过 `admin`、`role[]` 和 `permission[]` 三个状态字段驱动全局权限判断，路由守卫根据 `meta.guard` 结合用户角色和权限进行动态路由过滤。

### 两轨权限架构

系统将权限分为两条独立轨道，共用统一的资源路径格式和策略引擎，但授权主体和管理界面相对独立：

**Track A — 系统访问权限**——管控用户能看到哪些菜单、能执行哪些功能操作。通过角色绑定 + 菜单树分配 + 功能按钮配置实现，在路由守卫中以 `hasPermission()` 函数统一执行。

**Track B — IoT 控制权限**——管控用户能查看和控制哪些设备、空间和 MQTT Topic。通过 IAM 策略引擎，将主体（组织/部门/用户/服务账号）与资源路径（空间/楼栋/楼层/区域/设备/MQTT Topic）通过动作（view/read/write/control/subscribe/publish/admin）进行绑定，支持权限继承、DENY 覆盖和有效期控制。

### 统一资源路径命名空间

所有受权限管控的资源以统一路径格式表达，两轨共用：

**Track A（系统访问）**：
- `menu/{menuId}` —— 菜单项访问权限
- `micro/{serviceId}` —— 全局微服务访问权限
- `space/{spaceCode}/micro/{serviceId}` —— 园区内微服务访问权限
- `func/{functionCode}` —— 功能按钮/操作权限

**Track B（IoT 控制）**：
- `space/{spaceCode}` —— 园区级控制权限
- `space/{spaceCode}/bldg/{bldgCode}` —— 楼宇级控制权限
- `space/{spaceCode}/bldg/{bldgCode}/floor/{floorCode}` —— 楼层级控制权限
- `space/{spaceCode}/bldg/{bldgCode}/floor/{floorCode}/area/{areaCode}` —— 区域级控制权限
- `space/{spaceCode}/device/{deviceId}` —— 设备级控制权限
- `space/{spaceCode}/iot/topic/{pattern}` —— MQTT Topic 权限

路径支持 `*`（匹配任意段）和 `+`（MQTT 单级通配符），跨园区策略使用 `space/*` 前缀。

## 3.13.2 角色管理

### 功能入口

系统设置 → 人员管理 → 角色管理 / 权限控制 → 角色管理

### 功能描述

角色管理以数据表格和抽屉编辑表单为核心交互，支持系统角色的完整 CRUD 管理、菜单权限分配和功能按钮权限配置。

#### 角色类型体系

系统定义两种角色类型，通过 `role_type` 字段区分：

**系统角色（system）**——全局生效，不受空间（园区）限制。系统管理员（Admin）角色即属于此类型，可访问所有园区的全部菜单和功能。

**空间角色（space）**——仅在绑定的空间（园区）内生效。园区管理员（space-admin）、园区运营人员（space-operator）等角色的权限范围限定在指定园区。

角色列表支持按类型筛选（全部/系统角色/空间角色），角色名称和代码支持关键字搜索。

#### 角色列表

数据表格展示以下信息：
- **角色名称**——角色的显示名称
- **角色代码**——英文标识符（如 `space-admin`、`space-operator`），以等宽字体显示
- **角色类型**——系统角色（红色标签）/ 空间角色（蓝色标签）
- **适用范围**——系统角色显示"全部园区"，空间角色显示绑定的具体园区编码
- **适用平台**——PC端 / 移动端H5 / 全平台
- 操作——编辑、删除

#### 新建/编辑角色

点击"新增角色"按钮或"编辑"操作，弹出右侧抽屉（宽度 540px），配置以下字段：

**角色名称**（必填）——角色的中文显示名称。

**角色代码**（必填）——角色的英文标识符，建议使用英文短横线格式（如 `space-admin`、`device-operator`），用于后端权限判断和路由 guard 匹配。

**角色类型**（必填）——单选：空间角色（需绑定具体园区）/ 系统角色（全园区生效）。选择空间角色时，需额外选择绑定的园区（从空间列表下拉选择）。

**适用平台**（必填）——选择角色适用的终端平台：PC 管理端 / 移动端 H5 / 全平台。不同平台可配置不同的菜单权限。

**菜单权限分配**——以带复选框的树形组件（el-tree）展示全量菜单结构。管理员勾选该角色可访问的菜单节点，组件自动处理父子节点的全选/半选状态。菜单树的节点 key 为路由路径，标签为菜单标题。保存时将全选节点列表（`treeArray`）和半选父节点列表（`parentTreeArray`）一并提交。

**功能按钮权限**——以文本域形式配置该角色拥有的功能操作权限码，以逗号分隔（如 `read`、`write`、`delete`）。权限码与前端按钮的 `v-permission` 指令和后端接口的权限检查对应。

保存后，角色的菜单和按钮权限写入 `system_role` 表的 `menus` 和 `buttons` JSON 字段。删除操作内置保护逻辑——Admin、User、orgAdmin 三类内置角色不可删除，防止误操作导致系统不可用。

## 3.13.3 菜单权限控制

### 功能描述

菜单权限控制以三层机制协同实现：前端路由 guard、后端菜单 API 和角色菜单绑定。

#### 路由 guard 机制

所有前端路由可在 `meta.guard` 字段中配置访问权限要求。guard 支持两种格式：

**字符串数组**——`guard: ['Admin', 'space-admin']`，表示仅拥有这些角色之一或权限码之一的用户可访问。前端 `hasPermission()` 函数将用户角色列表和权限列表与 guard 数组做交集判断。

**GuardType 对象**——支持更复杂的匹配模式：
- `{ role: ['Admin'], permission: ['write'], mode: 'oneOf' }` —— 角色或权限满足任一即可（默认模式）
- `{ role: ['Admin'], permission: ['write'], mode: 'allOf' }` —— 角色和权限必须同时满足
- `{ role: ['blocked-role'], mode: 'except' }` —— 排除指定角色

**Admin 全通**——拥有 `Admin` 角色的用户（`aclStore.admin === true`）自动绕过所有 guard 检查，确保系统管理员始终可访问全部功能。

**空 guard 视为开放**——`guard` 为 `null`、`undefined` 或空数组 `[]` 的路由视为无限制，任意已登录用户均可访问。前端禁止将空数组 `[]` 作为 guard 值（在 JavaScript 中 `[]` 是 truthy，会导致权限检查误判）。

#### 动态路由过滤

前端在加载路由时通过 `filterRoutes()` 函数执行动态过滤：遍历所有路由节点，对每个节点检查其 `meta.guard`，若用户不满足 guard 要求则从路由树中剔除该节点。过滤在路由注册到 Vue Router 之前完成，确保无权访问的菜单在导航中完全不可见。路由过滤的结果同时用于侧边栏菜单的渲染——过滤后的路由树直接映射为侧边导航菜单。

#### 微服务双层开关

对于微服务类菜单，系统在角色菜单过滤之外额外增加一层微服务园区开关检查（详见第 3.13.5 节微服务配置）。两层都通过，菜单才对当前用户可见。此机制确保微服务的部署状态（是否在园区开通）和用户权限状态（是否拥有角色授权）解耦管理。

## 3.13.4 IoT 权限管理

### 功能入口

权限控制 → IoT 权限

### 功能描述

IoT 权限管理基于 IAM 统一策略引擎，以策略列表和抽屉编辑表单为核心交互，支持按组织（Org）、部门（Department）、用户（User）三级主体灵活配置 IoT 资源的操作权限。

#### 策略列表

数据表格展示所有 IoT 策略记录：
- **授权对象**——以彩色标签展示主体类型（组织/部门/用户）+ 主体名称
- **资源路径**——以等宽字体展示完整的 IAM 资源路径（如 `space/HZ001/bldg/B1/floor/F3/area/A01`），溢出时以 tooltip 显示全文
- **操作动作**——以彩色标签展示授予的动作集合（如 view、read、control、subscribe）
- **效果**——允许（绿色标签）/ 拒绝（红色标签）
- **是否继承**——对勾图标或叉号图标表示子资源继承状态
- **来源**——成员继承 / API / 手动，标识策略的创建方式
- **有效期**——过期日期，永久有效显示"永久"
- 操作——编辑、删除

顶部提供主体类型快速筛选（单选按钮组：组织/部门/用户），便于按主体维度快速定位策略。

#### 新建/编辑 IoT 策略

点击"新增策略"按钮弹出抽屉（宽度 560px），以四个分区（el-divider 分隔）配置策略参数：

**第一区：授权主体**
- 主体类型选择（单选按钮组：组织 / 部门 / 用户）
- 组织选择器（从组织列表下拉选择）
- 部门选择器（从部门列表下拉选择）
- 用户选择器（远程搜索，按姓名/工号模糊匹配，最短输入 1 字符）

**第二区：资源范围**
- 空间范围选择（单选按钮组）：当前园区 / 全部园区（`*`）/ 自定义园区
- 资源类型选择（下拉）：楼宇（bldg）/ 楼层（floor）/ 区域（area）/ 设备（device）/ IoT Topic（iot/topic）/ 微服务（micro）
- 资源标识输入（文本输入，支持通配符 `+` 单级匹配和 `*` 全匹配）
- **实时路径预览**——系统根据空间范围、资源类型和资源标识三个参数实时拼接生成完整的资源路径，以高亮文本框展示，如 `space/HZ001/device/D888`。此预览功能帮助管理员直观确认策略将覆盖的资源范围

**第三区：权限动作**
- **快捷预设按钮组**（三个预设组合，一键填充动作）：
  - 只读巡检：`[view, read, subscribe]`
  - 操作控制：`[view, read, control, subscribe]`
  - 完全权限：`[view, read, write, control, subscribe, publish]`
- 自定义权限（复选框组，双列布局）：
  - 读取类：view（可见）、read（读取数据）
  - 控制类：write（修改配置）、control（下发控制指令）
  - IoT 类：subscribe（订阅消息）、publish（发布消息）
  - 管理类：admin（管理子资源和向他人授权）

**第四区：策略控制**
- 效果选择（单选按钮组）：允许（Allow）/ 拒绝（Deny）。DENY 效果始终最高优先级，在任何层级的 DENY 立即生效，覆盖所有 ALLOW
- 继承子资源（开关）——开启后策略自动向下传播至所有子资源。例如授予某楼层的 view 权限并启用继承，则该楼层下的所有区域和设备自动获得 view 权限
- 有效期（日期时间选择器）——留空表示永久有效。过期策略在权限解析时自动忽略

#### 权限解析算法

IoT 权限的运行时解析遵循七步算法：

1. 获取用户属性：`user.orgId`、`user.departmentId`
2. 收集所有生效的 IAM 策略（`track='iot'`，`valid_from` / `valid_until` 在有效期内）：属于该用户的 user 级策略、属于该用户部门的 department 级策略、属于该用户组织的 org 级策略
3. 构建资源路径的祖先链（向上逐级）
4. 策略匹配：精确路径匹配 + 启用继承的祖先路径匹配
5. 优先级规则——DENY 效果：任何层级的 DENY 立即拒绝（无论主体层级）；ALLOW 效果：精确路径优先于继承路径，user 级优先于 department 级优先于 org 级；同层同路径有 DENY 和 ALLOW 共存时 DENY 胜出
6. 检查 valid_from / valid_until，过期策略忽略
7. 最终决策：有 ALLOW 且无 DENY → 允许；否则拒绝

## 3.13.5 微服务配置

### 功能入口

权限控制 → 微服务配置

### 功能描述

微服务配置以数据表格为核心，按空间（园区）维度控制各微服务的启用/停用状态，实现微服务的园区级可见性和可访问性管理。

#### 配置原理

微服务的访问权限由两层开关联合控制：
- **管理员维度**（本页面配置）——这个园区有没有部署/开通这个微服务？（`iam_micro_space` 表）
- **用户维度**（角色管理配置）——这个用户有没有权限访问这个微服务？（`system_role.menus`）

两层都通过，菜单才对用户在指定园区内可见。解耦运营配置（管理员决定园区开通哪些服务）与用户授权（角色决定用户拥有哪些菜单）。

#### 配置表格

表格以微服务为行、园区为列（动态列），直观展示每个微服务在各园区的启用状态：

- **微服务名称**——展示微服务的标题名称和英文代码标识
- **版本号**——微服务的当前版本
- **各园区列**（动态生成）——每个园区一列，以开关组件（el-switch）展示和切换该微服务在该园区的启用/停用状态
- **全部园区列**——以红色高亮开关控制全局启用/停用，开关操作即时生效

#### 操作效果

管理员点击某个园区的开关后，系统调用 `POST /iam/micro-space` 更新配置，前端自动调用 `routesStore.setRoutes()` 立即刷新侧边栏菜单——该园区内的用户菜单实时增删对应的微服务入口，无需用户刷新页面或重新登录。

## 3.13.6 成员管理

### 功能入口

权限控制 → 成员管理

### 功能描述

成员管理以组织和成员列表为核心交互，管理外租企业（Org）成员的入职/离职生命周期，实现权限的自动派生和级联回收。

#### 组织选择

页面顶部提供组织下拉选择器，加载全量组织列表。选择目标组织后，下方表格展示该组织的成员列表。切换组织时成员列表自动刷新。

#### 成员生命周期

**入职（添加成员）**——选择用户、填写部门（可选）和在组织内的角色（可选）后，系统创建 `iam_org_membership` 记录（状态为 active）。后端事件驱动逻辑自动执行：查询该组织（`subject_type='org'`, `subject_id=orgId`）的所有 IoT 策略，为该用户派生 `source_type='org_membership'`、`source_ref` 指向该成员记录 ID 的用户级策略副本。用户即时获得该组织所有 IoT 设备/空间的操作权限。

**权限继承说明**——界面以信息提示框说明自动继承机制："成员加入后，自动继承该组织的 IoT 设备权限；离职后，派生的权限自动失效。"

**离职（移除成员）**——将成员状态设为 `inactive` 后，系统自动执行：`UPDATE iam_policy SET valid_until=NOW() WHERE source_ref=membershipId`。所有从该组织派生的权限策略即时失效，用户立即失去对应的 IoT 控制能力。无需物理删除策略记录，满足安全审计要求——可随时查询"某用户在某时间段内拥有哪些权限"。

#### 成员列表

数据表格展示：成员姓名、所属部门、加入日期、状态（active 绿色 / inactive 灰色）、继承策略数量（点击可查看详情）、来源（手动 / API / HR同步）、操作（移除）。

## 3.13.7 服务账号管理

### 功能入口

权限控制 → 服务账号

### 功能描述

服务账号管理为 WallPad 面板、自动化策略引擎、系统集成接口等非自然人主体提供独立的认证与授权管理，实现 M2M（Machine-to-Machine）场景下的安全隔离。

#### 账号类型

- **WallPad**——安装在楼层墙面的智能控制面板，需获取对应楼层设备的 view 和 control 权限
- **Automation（自动化策略）**——Node-RED 等自动化引擎，需订阅 MQTT Topic 并发布控制指令
- **Integration（系统集成）**——第三方系统对接接口，需受限的读/写权限

#### 账号列表

数据表格展示：账号名称、账号类型（以彩色标签区分 WallPad 橙色 / Automation 蓝色 / Integration 绿色）、所属园区、Client ID、状态（active 绿色 / inactive 灰色）、操作（重置密钥 / 删除）。

#### 创建账号

弹出抽屉表单，配置：账号名称（必填）、账号类型（必填，三种类型）、所属园区（必填）、描述（可选）。创建成功后，弹出密钥展示对话框——显示 Client ID 和 Client Secret（各附带复制按钮），并明确警告："密钥仅在创建时展示一次，关闭后不可再次查看，请妥善保管。"

#### 鉴权机制

服务账号通过 `client_credentials` OAuth 流程获取访问 Token，Token 中携带 `service_account_id`。IoT 鉴权时 `subject_type='service_account'`，走同一套 `iam_policy` 引擎。与真实用户策略完全隔离——服务账号的策略和用户的策略互不干扰，管理界面也独立展示。

#### 重置密钥

点击"重置密钥"按钮后弹出确认对话框，确认后系统重新生成 Client Secret 并弹出展示。旧密钥立即失效，确保密钥泄露场景下的安全应急响应。

## 3.13.8 空间角色管理

### 功能描述

空间角色管理（Space Role）提供物理空间维度的权限授予能力，将使用者（组织/部门/用户）与楼层和区域的访问权限进行绑定，并支持日期时间调度控制。

#### 授权配置

空间角色编辑组件提供以下配置维度：

**授权对象**——通过组织树组件选择授权的目标主体，支持三种主体类型：组织（Org）、部门（Department）、用户（User）。

**空间范围**：
- 生效楼层——多选下拉框，从空间树加载楼层列表
- 排除楼层——多选下拉框，从已选生效楼层中排除特定楼层
- 生效区域——级联选择器（el-cascader），从空间树按楼栋 → 楼层 → 区域的层级加载可选区域

**实时生效范围计算**——系统根据"生效楼层 − 排除楼层 + 生效区域"的逻辑实时计算出最终的物理空间生效范围，以标签列表展示。

**日期时间调度**：
- 预设日期类型（多选）：工作日（周一至周五）、非工作日（周六日）、假期（如 2025 法定假期）
- 自定义日期——日期选择器支持添加特定日期（如特殊活动日、设备检修日），实现一次性授权场景

#### 空间树转换

`transformSpaceData()` 函数将原始空间层级树转换为级联选择器所需的数据格式，按区域类型（area / room / pubArea / mroom / toilet）过滤和重组节点。

## 3.13.9 门禁通行角色管理

### 功能入口

通行管理 → 通行权限 → 门禁角色

### 功能描述

门禁通行角色管理（Access Role）控制人员对物理门禁设备的通行授权，以门禁分组和有效期为核心控制维度。

#### 角色列表

数据表格展示：角色名称、权限分组（以标签展示关联的门禁分组，如旷视分组1/2/3）、关联用户数量、有效期范围（起始日期至结束日期）、描述、操作（编辑/删除）。

#### 新建/编辑门禁角色

弹出表单弹窗，配置：角色名称（必填）、权限分组（必填，多选：旷视分组1/2/3，每个分组对应一组门禁设备）、有效期起始日期（必填）、有效期截止日期（必填）、描述（文本域选填）。有效期满后权限自动失效，无需人工回收。

## 3.13.10 超出标书范围的能力

本系统在标书要求的 RBAC 角色权限和数据权限之外，额外提供以下增强能力：

**两轨统一权限引擎**——将系统访问权限（Track A：菜单、微服务、功能按钮）和 IoT 控制权限（Track B：设备、空间、MQTT Topic）统一到 `iam_policy` 策略表中管理。两轨共用相同的资源路径格式、策略匹配算法和效果优先级规则，但管理界面按业务场景分开暴露——系统权限由平台管理员配置，IoT 权限由园区运营人员配置，统一底层、分开界面的架构设计兼顾一致性和易用性。

**三级主体继承链（Org → Dept → User）**——IoT 权限可授予组织、部门和用户三级主体，形成权限继承链。解析优先级为精确匹配优先于继承匹配，user 级优先于 department 级优先于 org 级。DENY 效果在任何层级均立即生效且覆盖所有 ALLOW，支持"给整个部门开放某楼层权限，但拒绝某个特定用户的某区域权限"的精细调整。

**成员生命周期自动派生**——外租企业成员加入组织时，系统自动为该用户派生组织的全部 IoT 策略副本（`source_ref` 指向成员记录）；成员离职/移除时，系统自动设置所有派生策略的 `valid_until` 为当前时间，权限即时失效。全流程自动化，无需管理员逐一手动配置。派生策略记录永久保留，支持安全审计的权限回溯查询。

**微服务双层开关**——微服务接入由管理员维度（园区是否部署该服务，`iam_micro_space` 表）和用户维度（用户角色是否有该服务的菜单权限，`system_role.menus` 字段）两层独立控制，任一不满足即拒绝访问。开关切换后前端侧边栏菜单实时刷新，无需用户重新登录。

**空间角色日期时间调度**——空间角色授权支持按工作日/非工作日/假期/自定义日期配置时间调度。例如可配置"工作日白天可访问，周末和假期禁止访问"，实现基于时间的动态权限管理，适应不同时段的安防管理需求。

**服务账号 M2M 隔离**——WallPad 面板和 Node-RED 自动化引擎等服务组件通过独立的服务账号体系认证（`client_credentials` OAuth），走同一套 IAM 策略引擎但与真实用户完全隔离。密钥一次性展示、支持即时重置，满足 IoT 场景的安全运营要求。

**跨园区通配符支持**——IAM 资源路径支持 `*`（任意段匹配）和 `+`（单个段匹配）通配符。跨园区策略（`space/*`）可实现集团总部 IT 部门所有员工通行所有园区门禁的场景，配合精确园区的 DENY 策略实现例外隔离（某员工被排除在特定园区之外），兼顾跨园区便利性和单园区安全性。

**权限模拟调试工具**——系统提供权限模拟 API（`POST /iam/simulate`），输入用户 ID、动作、资源路径和园区编码后，返回权限判定结果（允许/拒绝）、匹配到的策略详情和完整的决策链（`chain`）。此工具用于调试复杂的策略配置和审计权限设计的合理性。
