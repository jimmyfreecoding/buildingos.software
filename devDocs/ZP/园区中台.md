# 3.1 园区中台

园区中台是智慧园区软件平台的核心能力汇聚层，向下对接各类异构子系统与 IoT 硬件设备，向上为业务应用提供统一的身份认证、消息推送、审批流转、权限管控、事件告警、系统集成与开放 API 等标准化能力。中台架构解耦了业务逻辑与底层基础设施，使得园区各业务场景（通行、访客、停车、能效、安防、会议、工单等）可以快速接入和协同运作，避免数据孤岛与重复建设。

---

## 3.1.1 应用统一入口

### 需求概述

为园区各类角色（运营人员、IT 管理员、物业人员、企业员工、访客）提供一站式的应用访问入口，在一个工作台中完成多项工作，避免多系统切换。同时为运营和 IT 人员提供统一的后台管理入口，按权限规则开放对应的配置能力。

### 统一身份认证体系

本方案基于 OAuth 2.0 标准协议构建园区统一身份认证中心，实现多端（Web 管理后台、H5 移动端、企业微信、小程序、IoT 设备面板）的统一登录与令牌管理。

**核心组件：**

| 组件 | 说明 |
|------|------|
| 身份验证服务器 (Authorization Server) | 中心化的身份验证服务，负责管理用户、设备和第三方应用的统一认证与授权，签发并验证 JWT 访问令牌 |
| 资源所有者 (Resource Owner) | 园区用户（运营人员、企业员工、访客等）及 IoT 设备，拥有对系统资源的访问权限 |
| 客户端 (Client) | Web 前端、H5 移动端、企业微信应用、小程序、IoT 设备固件、第三方集成系统 |
| 访问令牌 (Access Token) | JWT 格式令牌，包含用户身份、角色、空间编码、有效期等声明，所有 API 请求通过 `Authorization: Bearer <token>` 携带 |

**授权流程：**

```
用户/设备 → 客户端 → 认证服务器 → 签发 JWT Token
                ↓
        携带 Token 访问资源
                ↓
        资源服务器验证 Token → 授权/拒绝
```

通过此统一认证中心，可以实现以下多端登录场景：

1. **Web 管理后台登录**：用户名 + 密码登录，支持 RSA 非对称加密传输，Token 存储于 localStorage，支持自动刷新
2. **企业微信单点登录 (SSO)**：用户在企业微信客户端内点击应用入口，通过 OAuth 回调携带临时 token 完成免密登录，直接进入智脑物联网平台使用对应功能
3. **H5 移动端登录**：手机浏览器访问时提供的轻量级登录流程，适配移动端交互
4. **免密演示登录**：支持通过一次性链接（Demo-Login）实现免密跳转，适用于演示场景和临时授权访问
5. **IoT 设备凭证登录**：设备通过预置的 Client ID / Client Secret 获取令牌，用于设备面板（如墙装屏 WallPad）和自动化集成系统

### 统一工作台

登录后，系统根据用户角色和权限自动加载对应的导航菜单与功能模块。运营人员在一个工作台内即可完成：

- **IoT 设备监控**：实时查看楼宇照明、空调、门禁、电梯、传感器运行状态
- **场景策略编辑**：可视化配置自动化策略（照明定时、温控联动、AI 人密检测等）
- **告警处理**：接收、确认、处置各类设备告警，转换为工单跟踪
- **工单管理**：创建、派发、处置、验收全流程跟踪
- **数据看板**：通行、环境、能耗、安防、会议等综合运营仪表盘
- **权限管理**：组织架构维护、角色分配、IoT 资源授权
- **信息发布**：园区公告、终端屏幕内容编排与发布

### 组织人员同步

为确保统一入口下各系统的组织与人员信息保持一致，平台提供多种同步机制：

| 同步方式 | 说明 |
|----------|------|
| AD 域同步 | 对接企业 Active Directory，自动同步组织架构和人员信息 |
| API 同步 | 通过标准 REST API 实现与第三方 HR 系统（如钉钉、飞书通讯录）的数据同步 |
| 定时同步 | 按 cron 表达式定时执行全量或增量同步任务 |
| 手动同步 | 支持在管理后台手动触发立即同步 |
| 增量同步 | 通过 MQTT 消息 `/iot/action/user/increment/sync` 触发增量更新，仅同步变更数据，减少系统开销 |
| 企微绑定 | 支持通过二维码扫码将系统账号与企业微信账号绑定，打通企微与平台的身份映射 |

### 后台管理入口

系统为运营人员和 IT 人员提供统一的管理后台入口。基于 RBAC 权限模型，不同角色的用户登录后看到的菜单和功能模块不同：

- **园区运营人员**：设备监控、告警处理、工单管理、数据看板、信息发布、访客管理、通行管理等
- **IT 管理员**：用户管理、角色管理、菜单管理、API 设置、系统配置、备份管理、日志审计等
- **超级管理员 (Admin)**：拥有全部功能权限，可穿透所有空间的数据隔离查看全局视图
- **空间管理员**：仅管理指定空间（园区/楼栋）内的资源和数据

## 3.1.2 消息中心

### 需求概述

消息中心是园区中台的消息汇聚与分发枢纽，支持多场景消息模板配置、多渠道发送（飞书卡片消息 / 短信 / 邮件 / 系统内通知），对接飞书系统的消息推送与 Webhook，所有告警、工单状态变更、审批请求统一通过消息中心推送给相关人员。

### 消息汇聚

消息中心汇总展示所有业务模块产生的消息，按来源分类，包括但不限于：

| 消息来源 | 消息类型 |
|----------|----------|
| 设备告警 | 设备离线、阈值超限、故障告警 |
| 工单系统 | 工单创建、派发、处置完成、验收、超时提醒 |
| 审批流程 | 审批请求、审批通过、审批驳回 |
| 访客管理 | 访客预约通知、到访通知、签离通知 |
| 会议室 | 预定成功、会前提醒、抢占通知、会务服务工单 |
| 信息发布 | 发布审核通过、发布驳回 |
| 安防事件 | 门禁异常、消防告警、巡更异常 |
| 能效告警 | 能耗异常、碳排放超标 |

消息列表展示消息标题、来源模块、发送时间、接收人、发送渠道、阅读状态。需要进一步处理的消息（如待审批、待处置工单）支持点击快速跳转到对应的详情处理页面。

### 消息模板配置

系统支持为各类业务场景预设消息模板，模板中包含变量占位符，发送时根据实际业务数据动态填充：

```
模板示例（告警通知）：
标题：【告警通知】{deviceName} 发生 {alarmType}
内容：
  设备名称：{deviceName}
  设备位置：{spaceName} {floorCode} {areaName}
  告警类型：{alarmType}
  告警值：{alarmValue}
  告警时间：{alarmTime}
  请及时处理。
```

运营人员可在后台配置每种消息类型的模板、默认发送渠道、是否启用。

### 多渠道发送

| 渠道 | 适用场景 | 技术实现 |
|------|---------|----------|
| **飞书卡片消息** | 告警通知、审批推送、工单流转、会务服务 | 对接飞书开放平台 Bot API，支持交互式卡片（按钮、下拉菜单），点击直接跳转到对应处理页面 |
| **短信** | 紧急告警、访客通知、抢占提醒 | 对接短信网关 API |
| **邮件** | 运营报表、月度统计、审计日志 | SMTP 邮件服务 |
| **系统内通知** | 常规提醒、工单更新、系统公告 | WebSocket 实时推送 + 前端通知组件 |
| **MQTT** | IoT 设备指令、策略生效通知 | MQTT Broker 发布/订阅，Node-RED 消费 |
| **微信通知** | 访客预约通知、通行授权 | 对接微信模板消息 |

### 飞书深度集成

平台与飞书系统实现深度打通：

1. **飞书 Bot 消息推送**：通过飞书开放平台 Bot API 向指定用户或群组发送交互式卡片消息。告警卡片支持快捷操作（"确认接收"、"转工单"、"忽略"），审批卡片支持直接在飞书中完成审批
2. **飞书 Webhook 接入**：对接飞书自定义机器人 Webhook，支持将外部系统的告警/通知转发到飞书群
3. **消息链路追踪**：每条消息记录发送状态（待发送/已发送/发送失败/已读），失败自动重试，运营人员可在后台查看消息发送日志

## 3.1.3 审批流

### 需求概述

对接飞书审批流，为园区各类业务提供标准化审批能力。审批流程可灵活定义节点（审批人、审批条件、超时策略），支持在 Web 端和飞书移动端双端审批。

### 审批流引擎

本系统的审批引擎采用可配置的节点链式流程定义，支持以下节点类型：

| 节点类型 | 说明 |
|----------|------|
| 开始节点 | 审批流起点，定义触发条件和表单 |
| 审批节点 | 指定审批人（固定人员 / 按角色 / 按部门负责人），支持会签（全部通过）和或签（任一通过） |
| 条件分支 | 根据表单字段值动态路由到不同审批分支（如金额 > X 走高级审批） |
| 推送节点 | 审批通过/驳回后向飞书推送消息通知 |
| 归档节点 | 审批结束后将数据写入归档 |

### 审批场景覆盖

| 业务场景 | 审批流程示例 |
|----------|-------------|
| 信息发布审核 | 编辑提交 → 部门主管审核 → 园区管理员审核 → 发布 |
| 访客预约审批 | 访客申请 → 被访人确认 → 部门负责人审批 → 通知访客 |
| 会议室超时审批 | 预定超过阈值时长 → 部门经理审批 → 通过后生效 |
| 通行授权审批 | 临时人员通行申请 → 安保主管审批 → 下发门禁权限 |
| 工单处置审批 | 重大故障工单 → 逐级审批处置方案 → 执行 |

### 飞书审批流对接

- **飞书审批**：审批请求同步到飞书审批应用，审批人在飞书客户端内完成审批操作，审批结果回调到平台更新业务状态
- **双向同步**：在 Web 端审批与飞书端审批状态实时同步，避免重复审批
- **超时升级**：审批节点配置超时时间，超时未审批自动升级到上一级审批人或发送催办通知（飞书 / 短信）

### 审批记录与追溯

所有审批流程记录完整日志：发起时间、各节点审批人、审批意见、审批时间、最终结果。支持按时间范围、业务类型、审批状态、发起人进行检索和导出。

## 3.1.4 权限中心

### 需求概述

基于 RBAC 模型，支持按多种维度灵活配置角色权限，实现功能权限、菜单权限、数据权限的多维度精细化控制。权限自上而下具有继承关系，最小粒度可到单条 IoT 数据的读写控制。

### RBAC 权限模型

本系统的权限体系由三个核心维度构成：

```
┌─────────────────────────────────────────────────────┐
│                    权限模型                           │
│                                                      │
│  ┌──────────┐   ┌──────────────┐   ┌──────────────┐ │
│  │ 角色层    │   │ 菜单/功能层   │   │  数据权限层   │ │
│  │ (Role)   │   │ (Menu/Func)  │   │  (IotPolicy) │ │
│  ├──────────┤   ├──────────────┤   ├──────────────┤ │
│  │· Admin   │   │· 一级菜单可见  │   │· 空间范围     │ │
│  │· 运营主管 │   │· 二级菜单可见  │   │· 楼栋/楼层    │ │
│  │· IT管理员│   │· 按钮权限     │   │· 设备类型     │ │
│  │· 安保人员 │   │· 页面内Tab    │   │· IoT Topic   │ │
│  │· 自定义   │   │· API 接口     │   │· 读写/控制    │ │
│  └──────────┘   └──────────────┘   └──────────────┘ │
│                                                      │
│   用户 (User) ←→ 角色 (Role) ←→ 权限点 (Permission)   │
│         │                                           │
│         └──→ IoT 策略 (IamPolicy) ←→ 资源 (Resource)  │
└─────────────────────────────────────────────────────┘
```

**角色层级：**

| 角色类型 | 说明 | 示例 |
|----------|------|------|
| 系统角色 (System) | 系统内置，不可删除，拥有全量权限或按预设范围 | Admin（全量）、组织管理员（orgAdmin）、普通用户（User） |
| 空间角色 (Space) | 绑定到特定园区/空间，仅在该空间范围内生效 | 园区A运营主管、园区安保经理 |
| 自定义角色 | 管理员自定义创建，灵活配置权限点 | 访客管理员、工单处置员、设备巡检员 |

一个用户可以关联多个角色，权限取并集。Admin 角色拥有全局最高权限，绕过所有权限校验。

### 菜单权限控制

系统菜单采用树形结构管理，每个菜单项可以绑定权限标识。后端返回路由时，根据用户角色过滤可见菜单。菜单权限支持：

- **菜单可见性**：角色的菜单以勾选树的形式展现，管理员可为每个角色勾选可见的一级/二级/三级菜单
- **平台区分**：菜单区分 PC 端、手机端 (PHONE)、全平台 (ALL)，支持为不同终端定义不同的菜单集合
- **微服务开关**：按空间粒度控制微服务模块的启用/禁用（如某园区可关闭"停车管理"模块），刷新后菜单即时生效

### 功能权限控制

在菜单权限基础上，进一步细化到页面内的功能点（按钮、Tab、操作项）：

- **按钮级权限**：新增、编辑、删除、导出等操作按钮根据角色权限显示/隐藏
- **API 级权限**：后端接口层面校验角色权限，前端仅做 UI 层面的隐藏，最终安全由后端保障
- **通配符权限**：支持 `*` 通配符权限，拥有此权限的角色等同于全量访问

权限校验支持三种模式：

| 模式 | 说明 |
|------|------|
| `oneOf` | 拥有任一权限点即可访问 |
| `allOf` | 必须拥有全部指定权限点 |
| `except` | 排除模式，拥有指定权限点则拒绝 |

### 数据权限控制（IoT 资源策略）

针对 IoT 设备管理的精细化数据权限，本系统引入 ABAC（基于属性的访问控制）风格的 IoT 资源策略：

**策略组成：**

| 要素 | 说明 |
|------|------|
| 主体 (Subject) | 组织 (org)、部门 (department)、用户 (user) |
| 资源 (Resource) | 楼栋 (bldg)、楼层 (floor)、区域 (area)、设备 (device)、IoT 主题 (iot/topic)、微服务模块 (micro) |
| 操作 (Action) | 查看 (view)、读取 (read)、写入 (write)、控制 (control)、订阅 (subscribe)、发布 (publish)、管理 (admin) |
| 效力 (Effect) | 允许 (allow)、拒绝 (deny)，拒绝优先 |

**权限继承**：组织 → 部门 → 用户自上而下继承，子级自动拥有父级的权限策略。管理员可为组织/部门批量设置权限模板，新增成员自动继承。

**快速预设**：系统提供常见角色模板的快速预设（如"楼层管理员—仅查看本楼层设备状态"），一键应用到主体。

**资源路径预览**：配置策略时可预览实际影响的设备列表，确认权限的覆盖范围。

### 服务账号

面向非人身份（墙装屏 WallPad、自动化脚本、第三方集成系统），系统提供服务账号 (Service Account) 机制：

- 使用 Client ID + Client Secret 凭证对
- 支持 Secret 重置（重置后旧凭证立即失效）
- 可分配角色和 IoT 策略，权限与人账号一致
- 适用于系统间 API 调用、设备面板登录、自动化任务

## 3.1.5 账号管理

用户账号管理功能为所有平台用户提供个人账号信息维护能力。

### 个人信息管理

用户登录后可在个人中心查看和修改以下信息：

- **基本信息**：姓名、手机号、邮箱、头像
- **密码管理**：修改登录密码（需验证原密码，密码强度校验）
- **企业微信绑定**：通过二维码扫码绑定企业微信账号，实现 PC 端与移动端的身份打通

### 账号来源与编辑限制

| 账号来源 | 可编辑字段 | 限制说明 |
|----------|-----------|----------|
| 系统新建 | 全部字段 | 管理员可修改所有信息 |
| 组织同步 (AD/API) | 仅手机号、邮箱 | 姓名、部门等由上游系统维护，同步后自动更新 |
| 企微绑定 | 仅手机号 | 姓名和部门信息以企微通讯录为准 |
| SSO 单点登录 | 不可修改 | 账号信息由身份源系统管理，本平台不提供编辑入口 |

## 3.1.6 权限管理

### 3.1.6.1 用户管理

管理所有后台端和移动端的用户账号，提供完整的用户生命周期管理。

**用户列表**：展示系统所有账号，包含以下字段：

| 字段 | 说明 |
|------|------|
| 账号名 | 登录用户名 |
| 真实姓名 | 用户姓名 |
| 工号 | 企业内部工号 |
| 手机号 | 联系电话 |
| 邮箱 | 电子邮箱 |
| 所属组织 | 组织架构路径（如"中鹏集团 / IT部 / 系统运维组"） |
| 角色 | 用户关联的角色列表（支持多角色） |
| 状态 | 在职 / 离职 / 转岗 |
| 来源 | 系统添加 / 微信绑定 / 组织同步 |
| 项目权限 | 关联的园区/空间项目 |

**新建用户**：管理员通过录入姓名、登录账号、手机号、邮箱、所属组织、关联角色完成账号创建。如果用户数据由组织同步管理（AD/API），则不允许手动新建，需通过"组织架构 → 组织 → 新增成员"流程完成，确保数据一致性。

**编辑用户**：点击用户列表中的"修改"按钮可编辑用户信息、调整角色分配、修改所属部门。

**删除用户**：支持单个删除和批量删除，删除前二次确认。系统内置账号和同步来源账号受保护，不可删除。

**部门调动**：支持将用户从一个部门转移到另一个部门，调动后用户的组织路径和数据权限自动更新。

**企微绑定**：管理员可为未绑定企微的用户生成绑定二维码，用户使用企业微信扫码后完成账号关联，打通 PC 后台与企微移动端的身份。

**用户同步**：通过 MQTT 消息 `/iot/action/user/increment/sync` 触发增量同步，将变更的用户信息推送至各业务子系统（如门禁控制器、人脸识别终端）。

### 3.1.6.2 角色管理

管理所有后台用户角色，支持一个用户关联多个角色，权限取并集。

**角色列表**展示以下信息：

| 字段 | 说明 |
|------|------|
| 角色名称 | 角色的显示名称 |
| 角色类型 | 系统角色（内置）/ 空间角色 / 普通角色 |
| 创建类型 | 系统内置 / 自定义创建 |
| 组织架构 | 角色所属的组织范围 |
| 人数 | 当前拥有此角色的用户数量 |

**新增角色**：管理员可新增自定义角色，步骤为：
1. 输入角色名称
2. 选择所属组织（组织级角色仅在该组织范围内可见和分配）
3. 选择平台类型（PC 端 / 手机端 / 全平台）
4. 配置权限点：以勾选树的形式展示全部菜单和功能权限，按需勾选

**内置角色保护**：系统内置的 Admin、组织管理员 (orgAdmin)、普通用户 (User) 角色不可删除，仅可调整部分权限配置。

**编辑与删除**：自定义角色可编辑权限配置和删除。删除角色前系统检查是否有用户关联此角色，如有则提示先解除关联。

### 3.1.6.3 权限管理

权限管理是数据权限控制的核心模块，提供从组织到单条数据的精细化权限管控。

**权限继承关系**：权限自上而下具有继承关系：

```
组织 (Org)
  └── 部门 (Department)
        └── 用户 (User)
              └── 设备/资源
```

为组织设置的权限策略，该组织下所有部门和成员自动继承。部门可在此基础上叠加额外的权限策略。最小粒度可到单条 IoT 数据（某个具体设备的某个 Topic 的读写控制）。

**权限策略配置**：

| 配置项 | 说明 |
|--------|------|
| 主体 | 选择授权对象：组织、部门、或具体用户 |
| 资源类型 | 楼栋 (bldg)、楼层 (floor)、区域 (area)、设备 (device)、IoT Topic (iot/topic)、微服务模块 (micro) |
| 资源路径 | 支持精确匹配和通配符匹配。如 `ZP/A栋/1F/A区/*` 表示 A栋1F A区的所有设备 |
| 操作权限 | view（查看元数据）、read（读取数值）、write（写入配置）、control（发送控制指令）、subscribe（订阅消息）、publish（发布消息）、admin（管理权限） |
| 效力 | 允许 (Allow) / 拒绝 (Deny)。拒绝优先于允许，确保安全性 |

**前端功能权限**：后台配置的权限策略同时控制前端 UI 展示——用户仅看到有权操作的菜单、按钮和控制项，避免误操作。

**权限生效**：权限配置保存后即时生效，无需用户重新登录。前端在路由切换时实时校验权限，后端在每次 API 请求时校验。

### 场景联动引擎（Node-RED）

园区中台的核心联动引擎基于 Node-RED 构建：

1. **策略可视化编辑**：运营人员在前端通过时间轴表格（SenceView）可视化编排自动化策略——选择物理位置 × 日期类型 × 策略条件，定义定时任务或条件触发规则
2. **JSON 序列化**：策略保存后，前端通过 `transformSceneData()` 展平为按日期类型分组的执行数组，序列化为 JSON 存入后端
3. **Node-RED 消费**：Node-RED 读取策略 JSON，按日期类型索引当天规则，通过 cron 定时节点和时间条件节点执行
4. **热重载**：点击"立即生效"触发 MQTT 消息 `/iot/action/policy/valid`，Node-RED 收到后立即重新加载策略 JSON，无需重启
5. **设备指令下发**：Node-RED 通过 MQTT 向网关下发设备指令，网关再通过对应协议控制物理设备

## 3.1.8 开放平台

### 需求概述

提供标准化的开放 API 体系，覆盖 ≥90% 的平台核心能力；提供 API 文档发布、接口鉴权、访问频率限制、安全审计机制；提供标准化 SDK 开发包，支持第三方系统通过 SDK 快速集成和接入平台能力。

### 开放 API 体系

**API 设计标准：**
- RESTful 风格，统一使用 JSON 格式进行数据交换
- 统一的请求/响应格式：`{ code: string, msg: string, data: any }`
- 统一的错误码体系，便于第三方系统定位问题
- 支持分页、排序、字段过滤等通用查询能力

**API 覆盖范围（≥90% 平台能力）：**

| 能力域 | 开放 API 示例 |
|--------|-------------|
| 设备管理 | 设备列表查询、设备详情、设备状态、设备控制指令下发 |
| 空间管理 | 空间树查询、楼栋/楼层/区域信息、空间搜索 |
| 用户管理 | 用户信息查询、组织架构查询、角色查询 |
| 告警事件 | 告警列表查询、告警状态更新、告警统计 |
| 场景策略 | 策略配置查询、策略执行日志、策略触发 |
| 门禁通行 | 通行记录查询、门禁权限下发、远程开门 |
| 访客管理 | 访客预约创建、访客记录查询、访客通知 |
| 会议室 | 预定创建/取消、会议室查询、预定记录 |
| 停车 | 车辆出入记录、车位状态、黑名单查询 |
| 工单 | 工单创建、工单状态查询、工单流转 |
| 能耗 | 能耗数据查询、分项统计、趋势分析 |
| 数据看板 | 运营数据汇总、设备统计、告警概览 |

### 接口鉴权

| 鉴权方式 | 适用场景 |
|----------|---------|
| JWT Bearer Token | Web 端和移动端用户登录后调用，Token 有效期可配置，支持自动续期 |
| Client ID + Secret | 服务账号（Service Account），面向系统间集成和设备面板，Secret 可重置 |
| API Key | 轻量级鉴权，用于数据查询类接口和 Webhook 回调验证 |
| IP 白名单 | 可选的安全增强措施，仅允许指定 IP 范围访问开放 API |

### 访问频率限制

- **用户级限流**：基于用户 Token，默认 1000 次/分钟
- **应用级限流**：基于 Client ID，默认 5000 次/分钟
- **接口级限流**：关键接口（如设备控制）额外限制 60 次/分钟
- **超限处理**：返回 429 Too Many Requests，响应头中包含 `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset` 信息
- **白名单豁免**：内部关键系统可配置限流白名单

### 安全审计

- **API 调用日志**：记录每次 API 调用的调用方、接口路径、请求参数、响应状态、耗时、来源 IP
- **敏感操作审计**：设备控制、权限变更、用户增删等敏感操作单独记录审计日志，支持溯源
- **异常检测**：短时间内大量失败请求 → 自动告警；非白名单 IP 的敏感接口调用 → 标记审查
- **审计查询**：支持按时间范围、调用方、接口、状态码组合检索，支持导出 CSV/Excel

### 标准化 SDK

提供以下语言的 SDK 开发包，封装认证、签名、重试、错误处理等通用逻辑：

| SDK | 说明 |
|-----|------|
| JavaScript/TypeScript SDK | 面向 Web 前端和 Node.js 后端，npm 包发布 |
| Python SDK | 面向 AI 分析、自动化脚本、数据处理的 Python 开发者 |

**SDK 核心能力：**
- 统一的认证管理（JWT 自动续期、Client Secret 签名）
- 请求自动重试（指数退避，默认 3 次）
- 结构化错误处理（错误码 → 异常类型映射）
- 分页迭代器（自动翻页，透明化分页逻辑）
- TypeScript 类型定义（编译期类型检查）

**SDK 使用示例（TypeScript）：**

```typescript
import { BuildingOS } from '@buildingos/sdk'

const client = new BuildingOS({
  baseUrl: 'https://api.buildingos.ai',
  auth: { clientId: 'your-client-id', clientSecret: 'your-secret' },
  retry: { maxRetries: 3, backoff: 'exponential' },
})

// 查询设备列表
const { data } = await client.device.list({
  spaceCode: 'ZP',
  pageNo: 1,
  pageSize: 20,
})

// 下发控制指令
await client.device.control({
  deviceId: 'device-uuid',
  action: 'on',
  params: { temperature: 26, mode: 'cool' },
})

// 订阅设备状态变更
const unsubscribe = client.mqtt.subscribe('/iot/status/+/device-uuid', (msg) => {
  console.log('设备状态变更:', msg)
})
```

### API 文档发布

- **在线文档门户**：基于 Swagger/OpenAPI 3.0 规范生成交互式 API 文档
- **在线调试**：文档页面内可直接填入参数发起测试请求，实时查看返回结果
- **变更日志**：API 版本变更记录，含新增、废弃、Breaking Change 标注

## 3.1.9 事件与告警中心

### 需求概述

事件与告警中心是园区安全运营的神经中枢，汇聚来自设备、系统、业务的全量告警和事件数据，提供从告警产生、分级、通知、处置、升级到归档的全生命周期管理。

### 告警汇聚与统一展示

告警中心汇总以下来源的告警事件：

| 来源 | 告警类型 |
|------|---------|
| IoT 设备 | 设备离线、传感器阈值超限（温度/湿度/PM2.5/CO₂/TVOC）、通讯中断、电量过低 |
| 安防系统 | 门禁非法闯入、门未关好超时、消防烟感触发、视频移动侦测、巡更异常 |
| 能效系统 | 用电异常、用水异常、能耗超标 |
| 楼宇自控 | 空调故障、照明回路故障、电梯困人 |
| 网络 | 网关离线、交换机端口 Down、WiFi AP 离线 |
| 系统 | 服务异常、数据库连接失败、消息队列积压 |
| 业务 | 工单超时未处置、审批超时未处理 |

**告警看板**：以仪表盘形式展示告警全貌：

- **概览卡片**：告警总数、已处理数、处理中数、待处理数、响应率、平均响应时间
- **趋势图**：近 7 天/30 天告警趋势（柱状图 + 折线图）
- **来源分布**：告警来源系统分布（横向柱状图）
- **空间分布**：各园区/楼栋告警数量分布（饼图）

**告警列表**：支持按以下维度筛选和检索：

- 告警时间范围
- 告警类型（设备告警 / 空调告警 / 环境告警等）
- 告警等级（高 / 中 / 低）
- 处理状态（未接收 / 已接收 / 处理中 / 误报 / 已处理）
- 关键字搜索（设备名称、告警内容）
- 空间树筛选（园区 → 楼栋 → 楼层）

### 告警分级与处理流程

**告警等级：**

| 等级 | 颜色 | 定义 | 响应要求 |
|------|------|------|---------|
| 高 (Critical) | 红色 | 影响人身安全或核心业务中断（如消防告警、电梯困人、主干网络中断） | 5 分钟内响应 |
| 中 (Warning) | 橙色 | 部分功能受影响，需及时处理（如设备离线、空调故障、门禁异常） | 30 分钟内响应 |
| 低 (Info) | 蓝色 | 一般性提醒，不影响业务（如设备电池低电量、定期维护提醒） | 2 小时内响应 |

**处理流程：**

```
告警产生 → 告警分级 → 通知推送(飞书/短信/邮件)
                ↓
          运营人员接收
                ↓
     ┌────── 确认为误报 → 标记"误报" → 归档
     │
     └────── 确认有效 → 处理中
                ↓
          ┌─ 可直接处理 → 处理完成 → 填写处理说明 → 归档
          │
          └─ 需工单跟进 → 一键转工单 → 派发 → 处置 → 验收 → 归档
```

### 告警通知与推送

告警产生后，系统根据告警等级和来源自动匹配通知策略：

- **高等级告警**：飞书卡片消息 + 短信 + 系统弹窗（三重通知）
- **中等级告警**：飞书卡片消息 + 系统内通知
- **低等级告警**：系统内通知

通知内容包含：告警标题、设备名称、位置信息、告警值、告警时间、"确认接收"和"转工单"快捷操作按钮。

### 告警升级 (Escalation)

对于超时未处理的告警，系统支持自动升级：

| 配置项 | 说明 |
|--------|------|
| 升级条件 | 告警产生后 N 分钟内未被接收/处理 |
| 升级目标 | 上一级负责人、部门主管、或指定的升级接收人 |
| 升级通知方式 | 飞书 / 短信 / 电话（按告警等级配置） |
| 最大升级次数 | 可配置，超过后标记为"升级终态"并通知最高级管理员 |

以安防告警为例，典型升级链：值班安保员（5分钟未处理）→ 安保主管（10分钟）→ 园区负责人（15分钟）。

### 告警聚合与去重

- **时间窗口聚合**：同一设备在 N 分钟内重复产生的同类告警自动合并为一条告警记录，告警次数递增，避免告警风暴
- **设备级去重**：同一设备的同一告警类型在未处理期间仅保留一条活跃告警

### 告警白名单与静默

- **时间静默**：在指定时间段内（如设备维护窗口），特定设备或区域的告警自动抑制
- **设备白名单**：测试设备、已报修设备加入白名单，不产生告警
- **告警类型屏蔽**：可针对特定空间屏蔽某类告警（如装修期间的烟感告警）

### 消防联动

消防告警触发后的自动化联动：

1. 消防主机 → 平台接收火警信号
2. 自动打开对应楼层所有门禁（断电释放）
3. 自动切换对应区域摄像头到监控大屏
4. 推送消防告警到所有相关人员（安保、园区负责人）
5. 生成消防事件记录（含视频截图、门禁状态快照）

### 告警与工单联动

告警可一键转为工单，自动填充工单信息：

- 故障设备名称和位置（从告警信息自动带入）
- 告警描述（作为工单描述）
- 建议处置人（根据设备类型和区域自动推荐）
- 优先级（根据告警等级映射）

工单处理完成后，告警状态自动同步更新，形成完整的"告警 → 工单 → 处置 → 验收 → 归档"闭环。

### 历史回溯与报表

- **告警历史**：按时间轴展示任意时间段的告警记录，支持回放分析
- **导出**：支持按筛选条件导出告警日志为 Excel/CSV
- **告警统计**：月度告警趋势、告警类型分布、处理效率趋势等统计报表

#### 数据清洗机制

系统在 Node-RED 数据编排层实现了多层数据清洗流水线，确保异常数据在入库前被拦截：

**1. 阈值校验**

| 校验类型 | 说明 | 示例 |
|----------|------|------|
| 绝对值范围 | 传感器读数超出物理可能范围则丢弃 | 温度传感器上报值 > 100°C 或 < -40°C → 标记异常，不入库 |
| 变化率检测 | 相邻两次上报值变化超过合理斜率则标记可疑 | 温度在 1 秒内变化超过 10°C → 标记跳变异常 |
| 死区过滤 | 值变化小于配置的死区阈值不上报/不入库 | 温度变化 < 0.1°C → 视为噪声，丢弃 |
| 枚举校验 | 状态类数据必须为预定义枚举值 | 设备状态值不在 {0,1,2} 中 → 丢弃 |

**2. 异常值处理策略**

```
传感器上报数据
    │
    ├── 数值类型检查 ── 非数值 ──→ 丢弃 + 计数
    │
    ├── 阈值范围检查 ── 超限 ──→ 标记 "boundary_violation" + 不入库 + 告警
    │
    ├── 变化率检查 ──── 跳变 ──→ 标记 "spike_detected" + 入库(带标记字段) + 通知
    │
    ├── 死区检查 ────── 噪声 ──→ 丢弃（变化 < 阈值）
    │
    └── 通过全部检查 ──────────→ 正常入库
```

**3. 空值/缺失值处理**

- **采集层空值**：设备上报数据中必填字段为空时，整条记录丢弃并触发设备数据质量告警
- **传输层缺失**：MQTT 消息解析失败时，原始报文写入死信队列 (Dead Letter Queue) 供后续排查，不入时序库
- **应用层空值**：查询时对于时间窗口内缺失的数据点，返回 `null` 而非填充虚假值，上层业务自行决定插值策略

#### 数据去重

针对网络重传、网关缓存重放等场景导致的重复数据，系统在入库环节实现去重：

| 策略 | 实现方式 | 适用场景 |
|------|---------|----------|
| 时间戳+设备唯一键去重 | TDengine 表级 `PRIMARY KEY (ts, device_id)`，相同时间戳+设备的数据 INSERT 时自动覆盖 | 同一设备同一时间戳重复上报 |
| 消息 ID 去重 | Node-RED 节点维护滑动窗口（最近 N 条 msgId），收到重复 msgId 直接丢弃 | 网关缓存重放 |
| 时序窗口去重 | 同一设备在 X 秒窗口内数值完全相同的多条记录合并为一条 | 传感器高频采样降噪 |

去重策略可针对不同设备类型灵活配置参数（窗口大小、去重维度），平衡数据精度与存储成本。

#### 数据补传与离线回填

网关或设备因网络中断、断电等原因离线期间，本地缓存采集数据，待网络恢复后将历史数据批量回补到平台。

**补传机制设计：**

```
设备正常运行
    │
    ├── 网络正常 ──→ 实时上报 ──→ 正常入库
    │
    └── 网络中断
          │
          ├── 设备/网关本地缓存 (环形缓冲区, 容量 ≥ 7天数据量)
          │     │
          │     └── 每条数据标记: { deviceTime, cacheSeq, quality: "cached" }
          │
          └── 网络恢复
                │
                ├── 实时数据恢复上报（恢复正常通道）
                │
                └── 历史缓存数据批量回补（补传通道, 限速避免冲击）
                      │
                      └── 按时间戳顺序逐条入库
```

**补传数据标识：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `data_source` | ENUM | `realtime`（实时）/ `backfill`（补传）/ `manual`（人工录入） |
| `device_time` | TIMESTAMP | 数据实际产生的时间（设备时钟），区别于入库时间 `ts` |
| `cache_seq` | INT | 设备缓存序列号，用于判断是否丢包 |
| `backfill_batch_id` | STRING | 本次补传的批次 ID，用于追踪和审计 |

**补传保障措施：**

- **限速回填**：补传数据以低于实时数据的优先级入队，限速写入避免冲击正常业务
- **断点续传**：补传过程中再次断网，恢复后从上次断点继续，不重复传输
- **完整性校验**：补传结束后比对缓存 seq 序列，缺失的数据段自动申请重传
- **补传监控**：平台展示各网关/设备的补传状态（补传中/已完成/有缺失），支持手动触发补传

#### 时序数据库（TDengine）

本系统选用 **TDengine** 作为 IoT 时序数据存储引擎，相比通用关系型数据库，在物联网场景下有数量级的写入性能和存储压缩优势。

**核心设计：**

| 设计要点 | 说明 |
|----------|------|
| 超级表 (STable) | 按设备类型创建超级表（如 `sensor_temperature`、`meter_electric`），定义公共 Schema |
| 子表 (Table) | 每个物理设备一张子表，继承超级表 Schema，独立存储，互不影响 |
| 标签 (Tag) | 每张子表附加静态标签（设备编码、设备名称、空间编码、楼栋、楼层、区域、设备类型），用于快速检索和分组聚合 |
| 自动分区 | 按天或按月自动创建数据分区，查询时利用分区裁剪大幅缩小扫描范围 |
| 写入性能 | 单节点支持百万级数据点/秒写入，满足大规模园区设备高频采集需求 |

**数据保留策略（5 年）：**

```
数据生命周期：
├── 0 ~ 12 个月（热数据）
│   ├── 存储于 SSD 高速存储
│   ├── 原始精度保留（采集周期 = 设备原始采样频率）
│   └── 支持任意维度实时查询和聚合分析
│
├── 12 ~ 36 个月（温数据）
│   ├── 存储于 HDD 大容量存储
│   ├── 原始精度保留
│   └── 查询延迟略高于热数据（秒级）
│
└── 36 ~ 60 个月（冷数据）
    ├── 存储于 HDD 归档存储
    ├── 自动降精度聚合（原始数据 → 小时级聚合 + 日级聚合）
    ├── 保留关键统计值（min/max/avg/count）
    └── 支持趋势分析和年度对比查询
```

**TTL 自动清理：** TDengine 在创建表时设定 `TTL = 1825d`（5 年），到期数据由数据库引擎自动清理，无需人工干预。超过保留期的数据在清理前可导出为 Parquet 格式归档文件供合规备查。

**数据压缩：**

| 压缩技术 | 说明 | 压缩效果 |
|----------|------|----------|
| ZLIB 无损压缩 | TDengine 内置列式压缩，对时序数据的时间戳差分编码（Delta-of-Delta）+ 数值 XOR 编码后进行 ZLIB 压缩 | IoT 场景典型压缩比 10:1 ~ 20:1 |
| 列式存储 | 同一列数据连续存放，相同类型数值聚集度高，压缩效率远超行式存储 | 配合 ZLIB 实现更高压缩比 |
| 降精度归档 | 超过 3 年的冷数据自动按小时/天聚合，仅保留统计值，大幅减少存储占用 | 冷数据存储量降低 90%+ |

**多维查询支持：**

| 查询维度 | 示例 |
|----------|------|
| 按时间范围 | `WHERE ts >= '2026-01-01' AND ts <= '2026-01-31'` |
| 按设备编码 | `WHERE device_id = 'sensor_temp_A1_001'` |
| 按空间层级 | 通过 Tag 检索：`WHERE space_code = 'ZP' AND building = 'A栋' AND floor = '1F'` |
| 按设备类型 | 通过超级表直接查询：`FROM sensor_temperature WHERE area = 'A区办公区'` |
| 聚合查询 | `SELECT AVG(value), MAX(value), MIN(value) FROM sensor_temperature WHERE ts >= NOW - 7d INTERVAL(1h)` |
| 降精度查询 | `SELECT AVG(value) FROM meter_electric WHERE ts >= '2026-01-01' AND ts <= '2026-12-31' INTERVAL(1d)` |
| 多表 JOIN | TDengine 支持超级表间的 JOIN 查询，可按空间编码关联不同设备类型进行联合分析 |

**查询性能保障：**

- **分区裁剪**：按时间范围查询时，TDengine 自动跳过不相关分区，仅扫描目标分区
- **标签索引**：在 Tag 列上建立索引，按空间/设备/类型过滤时快速定位目标子表
- **缓存机制**：热数据常驻内存缓存（LRU），常用聚合查询结果缓存
- **查询下推**：聚合计算在数据库层面完成，仅返回聚合结果，减少网络传输和应用层计算开销

#### Node-RED 数据编排

Node-RED 不仅是场景联动的执行引擎，也是数据治理流水线的编排工具。通过可视化的拖拽式流程编辑器，运维人员可以灵活定义数据处理逻辑：

**数据治理相关节点：**

| 节点类型 | 功能 | 说明 |
|----------|------|------|
| MQTT In | 数据接入 | 订阅设备数据主题 `/iot/data/#`，接收原始设备报文 |
| Function | 自定义处理 | JavaScript 编写数据处理逻辑：阈值校验、格式转换、单位换算 |
| Filter | 条件过滤 | 基于规则过滤异常数据，如 `value < -40 OR value > 100 → drop` |
| Delay/Debounce | 防抖去重 | 配置时间窗口内的去重逻辑 |
| Switch | 路由分发 | 正常数据入库，异常数据路由到告警主题 |
| TDengine Out | 数据写入 | 将处理后的数据写入 TDengine 超级表 |
| Debug | 调试监控 | 实时查看数据流水线中每个节点的数据样本 |

**典型数据处理流示例（温度传感器）：**

```
MQTT In (/iot/data/temperature/#)
    │
    ├── JSON Parse (解析 payload)
    │
    ├── Function: 阈值校验
    │     if (value > 100 || value < -40) → msg.quality = "rejected"
    │     else if (delta > 10) → msg.quality = "spike"
    │     else → msg.quality = "normal"
    │
    ├── Switch: 分流
    │     "rejected" → MQTT Out (/iot/alarm/data/quality) + 丢弃
    │     "spike"   → MQTT Out (/iot/alarm/data/spike) + 继续入库(标记)
    │     "normal"  → 继续
    │
    ├── Function: 添加元数据
    │     注入 device_name, space_code, building, floor, area (从 Tag 缓存获取)
    │
    └── TDengine Out: 写入 sensor_temperature 超级表
```

#### 数据质量监控

系统提供数据质量的量化监控指标，帮助运营团队掌握 IoT 数据的整体健康状况：

| 指标 | 计算方式 | 告警阈值 |
|------|----------|----------|
| 数据完整率 | 实际入库数 / 理论应采集数 × 100% | < 95% 触发告警 |
| 异常值占比 | 被拦截的异常记录数 / 总采集数 × 100% | > 5% 触发告警 |
| 采集延迟 | `ts(入库)` - `device_time(采集)` | > 60s 触发告警 |
| 补传数据量 | 当日补传记录总数 | > 理论值的 30% 触发告警 |
| 设备离线时长 | 最后上报时间距当前时间的间隔 | > 10min 触发告警 |

这些指标在告警看板中以仪表盘形式展示，支持按空间（园区/楼栋/楼层）和设备类型下钻分析。
