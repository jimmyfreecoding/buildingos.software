# 数据治理方案

## 一、数据治理架构概述

BuildingOS AI 数据治理覆盖从设备数据采集、传输、清洗、存储到查询的全链路，核心数据管道如下：

```
IoT设备 → MQTT (EMQX) → Node-RED (边缘清洗) → MQTT → Go-Bridge (批处理) → TDengine (时序存储)
                                │                                    │
                         离线状态过滤                          共享订阅消峰
                         类型转换/格式化                       批量写入(500条/200ms)
                         网关设备匹配校验                      多表SQL构建
                                │                                    │
                                └─────────── 告警直写 ───────────────┘
                                         (systemalarm STable)
```

## 二、数据清洗

### 2.1 多层清洗策略

系统在数据进入时序数据库之前设置了三道清洗关卡：

**第一关：Node-RED 边缘预处理**

设备上报的原始数据首先经过 Node-RED 流程节点处理：

- **离线状态过滤**：检查设备在线状态（`status.online`），离线设备数据直接丢弃，防止脏数据写入
- **网关/设备匹配校验**：校验 `gateway` 和 `layer`（设备所属楼层区域）是否存在且与数据库记录匹配，不匹配的数据跳过不处理
- **数据类型规范化**：所有传感器数值统一做 `parseInt()` / `parseFloat()` 类型转换，非数值字符串转为合法数值，无效格式丢弃
- **必填字段校验**：检查 `msg.payload` 是否为数组结构，保证数据结构完整性

**第二关：Go-Bridge 格式校验**

- **JSON 合法性验证**：非合法 JSON 格式的消息记录告警并丢弃
- **Topic-表映射校验**：消息 MQTT Topic 必须在映射配置中存在对应关系，未配置 Topic 的消息跳过
- **字段类型强制转换**：根据配置的字段类型（`ts` 时间戳、`num` 数值、`str` 字符串）进行格式化，非法值转为 NULL 而非阻塞写入

**第三关：TDengine Schema 约束**

- 超级表（STable）列定义严格限定字段类型（TIMESTAMP / INT / FLOAT / NCHAR）
- 类型不匹配的数据写入时被 TDengine 内核拒绝，并记录错误日志

### 2.2 异常值处理原则

- 设备层异常（离线、故障）：在 Node-RED 层拦截，不入库
- 数据格式异常（非 JSON、字段缺失）：在 Go-Bridge 层拦截，不入库
- 数据值异常（超出物理范围）：当前不做范围校验，保留原始数据，供上层业务分析判断

> **设计考量**：传感器数值的"正常范围"因设备型号、安装环境差异极大，硬编码阈值容易误杀有效数据。系统采用"入库留痕 + 上层标记"策略，将异常值判定交由业务分析层处理。

## 三、数据去重

### 3.1 EMQX 共享订阅机制

Go-Bridge 采用 EMQX 共享订阅（Shared Subscription）模式消费 MQTT 消息：

```
订阅主题: $share/go-bridge/<原始Topic>
```

- EMQX 在多个 Go-Bridge 实例间以轮询（round-robin）方式分发消息
- 同一条消息只会被一个消费者处理，从根本上避免多实例重复写入
- 支持多副本水平扩展而不产生重复数据

### 3.2 TDengine 子表唯一性

每条设备数据写入独立的 TDengine 子表（Child Table），子表命名规则为 `{STable}_{device_code}`。同一设备的数据始终写入同一个子表。当设备上报同时间戳的重复数据时，TDengine 会覆盖写入（upsert 语义），自动合并重复记录。

### 3.3 业务数据去重

PostgreSQL 业务表层面，通过数据库唯一约束和主键保证数据不重复：

| 约束类型 | 示例 |
|----------|------|
| 主键约束 | `user.id`、`device.id`、`space.id` |
| 唯一索引 | `workstation.code`（工位编码唯一） |
| 复合唯一索引 | `external_identity(provider, tenantId, externalUserId)` |

## 四、数据补传机制

### 4.1 设备端自动重连

IoT 设备在离线恢复后通过 MQTT 协议自动重连 EMQX Broker（重连间隔 5 秒），连接恢复后立即开始上报当前实时数据。

### 4.2 MQTT Bridge 断线续传

边端 EMQX → 云端 EMQX 通过 MQTT Bridge 连接，配置如下：

- **重试间隔**：15 秒
- **最大并发**：100 条消息并行传输
- **QoS 等级**：1（至少一次送达）

桥接链路断开后以 15 秒间隔持续重试，恢复后自动续传积压消息。

### 4.3 PostgreSQL 逻辑复制自动恢复

边缘节点 PostgreSQL（只读影子库）与云端主库通过逻辑复制（Publication/Subscription）保持同步：

- **自动检测**：定时检测影子表是否缺失、复制槽是否丢失
- **自动修复**：发现缺失时自动重建表结构、刷新发布、重建订阅
- **WAL 保留**：云端 PG 配置 `max_slot_wal_keep_size = 1GB`，边端离线期间保留 WAL 日志供恢复

### 4.4 补传数据标识

边端离线期间设备本地缓存的时序数据，在恢复连接后通过 MQTT Bridge 回传至云端。回补数据在 TDengine 中写入时自带原始设备时间戳（`ts` 字段），与实时数据使用相同的数据管道，可通过时间戳范围识别回补数据的归属时段。

### 4.5 设计权衡

| 数据类型 | 补传策略 | 说明 |
|----------|----------|------|
| 设备元数据（空间/网关/设备主数据） | 全量自动恢复 | PG 逻辑复制保障 |
| 高频时序数据（传感器读数） | 摘要聚合 + 关键事件 | 断网期间原始高频数据量巨大，自动全量回传可能阻塞实时通道 |
| 告警事件 | 实时补传 | 离线期间告警恢复后即时上报 |
| 通行记录 | 批量补传 | 门禁设备本地存储，联网后批量同步 |

## 五、时序数据库存储

### 5.1 数据库选型

选用 **TDengine 3.3** 作为物联网时序数据存储引擎，是国产开源时序数据库，专为 IoT 场景优化：

- **写入性能**：比通用数据库高 10 倍以上（单节点百万点/秒）
- **存储压缩**：列式存储 + 差值编码，压缩比可达 10:1
- **标准 SQL**：支持标准 SQL 查询，兼容 JDBC/ODBC/RESTful 接口

### 5.2 数据保留策略

TDengine 数据库配置如下：

```sql
CREATE DATABASE IF NOT EXISTS bxserver KEEP 365;
```

- **默认保留期**：365 天（12 个月），满足标书 "≥ 12 个月" 的要求
- **超期自动清理**：超过保留期的数据块由 TDengine 内核自动删除，无需人工干预
- **可按需延长**：通过 `ALTER DATABASE bxserver KEEP 730` 延长至 24 个月或更长

### 5.3 超级表设计

系统定义了 16 张超级表（STable），覆盖全部 IoT 设备类型：

| 序号 | 超级表 | 数据内容 | 标签维度 |
|------|--------|----------|----------|
| 1 | `airsensor` | 空气质量（PM2.5/PM10/TVOC/CO₂/甲醛/温湿度等 20+ 指标） | 9 标签 |
| 2 | `humensensor` | 人体存在感应 | 9 标签 |
| 3 | `aicamerasensor_densitycount` | AI 摄像头人流密度统计 | 9 标签 |
| 4 | `aicamerasensor_crosscount` | AI 摄像头越界计数 | 9 标签 |
| 5 | `aicamerasensor_smokingcall` | AI 摄像头吸烟检测 | 9 标签 |
| 6 | `aicamerasensor_face_recognition` | AI 摄像头人脸识别 | 9 标签 |
| 7 | `smokesensor` | 烟雾传感器 | 9 标签 |
| 8 | `powersensor_loop` | 电力回路监测 | 9 标签 |
| 9 | `powersensor` | 电力总表（三相电压电流功率） | 9 标签 |
| 10 | `wcsensor` | 卫生间厕位传感器 | 9 标签 |
| 11 | `systemalarm` | 系统告警事件 | 9 标签 |
| 12 | `pad` | 信息发布屏状态 | 9 标签 |
| 13 | `door_pass_log` | 门禁通行记录 | space |
| 14 | `iot_control_log` | 设备控制操作日志 | space/floor_area/floor/area |
| 15 | `elevator` | 电梯运行状态 | space |
| 16 | `weather` | 天气数据 | space |

### 5.4 标签（Tag）体系

每张超级表配置标准化标签，支持按空间维度高效查询：

| 标签 | 类型 | 说明 |
|------|------|------|
| `position` | NCHAR(200) | 设备在空间树中的层级路径 |
| `space` | NCHAR(20) | 园区/空间编码 |
| `floor_area` | NCHAR(20) | 楼层区域编码 |
| `floor` | NCHAR(20) | 楼层 |
| `area` | NCHAR(20) | 区域编码 |
| `device_code` | NCHAR(50) | 设备编码 |
| `device_id` | INT | 设备数字 ID |
| `factory` | NCHAR(50) | 设备厂商 |
| `model` | NCHAR(50) | 设备型号 |

### 5.5 多维度查询支持

基于 TDengine 标签体系 + 标准 SQL，系统支持以下维度的时序数据查询：

| 查询维度 | 实现方式 | 示例 |
|----------|----------|------|
| 时间范围 | WHERE ts >= start AND ts <= end | 查询过去 24 小时数据 |
| 设备编码 | WHERE device_code = 'xxx' | 查询指定设备 |
| 空间/园区 | WHERE space = 'park_a' | 查询某园区全部设备 |
| 区域 | WHERE area = 'zone_01' | 查询某区域设备 |
| 楼层 | WHERE floor = 'F1' | 查询某楼层设备 |
| 复合查询 | 多 WHERE 条件组合 | 查询某园区某楼层过去 7 天数据 |

查询接口同时支持跨时间段的聚合运算（`AVG`、`MAX`、`MIN`、`SUM`）和降采样（INTERVAL 时间窗口）。

### 5.6 实时流式计算

TDengine 内置流计算引擎，系统预置 2 条 Stream 实现实时聚合：

- **会议室占用聚合**：人体传感器数据 1 分钟窗口实时聚合，计算会议室占用状态
- **人流密度聚合**：AI 摄像头密度计数 1 分钟窗口聚合，输出区域人流量趋势

## 六、数据管道高可用

### 6.1 Go-Bridge 批处理

| 参数 | 值 | 说明 |
|------|-----|------|
| 批量大小 | 500 条 | 累积 500 条自动刷新 |
| 刷新间隔 | 200ms | 超时自动刷新，防止低流量时数据积压 |
| QoS | 1 | MQTT 至少一次送达保证 |
| 共享订阅 | `$share/go-bridge/` | 多副本负载均衡消费 |

### 6.2 错误处理

| 环节 | 处理策略 |
|------|----------|
| JSON 解析失败 | 记录告警日志并丢弃 |
| Topic 无映射 | 静默跳过 |
| TDengine 写入失败 | 记录错误日志（当前不重试，避免阻塞管道） |
| MQTT 连接断开 | 自动重连，恢复后继续消费 |

## 八、治理能力对标

| 标书要求 | 系统实现 | 达标 |
|----------|----------|------|
| 数据清洗：异常值不入库 | 三层过滤（设备状态 + 格式校验 + Schema 约束） | ✓ |
| 数据去重：同设备同时间只保留一条 | EMQX 共享订阅 + TDengine Upsert + PG 唯一约束 | ✓ |
| 补传机制：离线数据恢复回补 | MQTT Bridge 自动重连续传 + PG 逻辑复制自动恢复 + WAL 保留 | ✓ |
| 时序数据库：保留 ≥ 12 月 | TDengine KEEP 365 天，支持延长配置 | ✓ |
| 多维度查询：时间/设备/区域 | 9 维度标签体系 + 标准 SQL 多维查询 | ✓ |
| 开源数据库，非私有格式 | TDengine AGPL v3 开源 + PostgreSQL 开源 | ✓ |
